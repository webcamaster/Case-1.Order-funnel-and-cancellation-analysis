# Data quality: Кейс 1 — воронка заказов

Отчёт о проверке качества данных и принятых допущениях.
Каждый пункт: проблема → масштаб → решение → влияние на анализ.

**Период данных:** 24.08.2022 – 08.09.2022 (16 дней).
Первый и последний дни неполные (данные начинаются в 01:52 24.08
и обрываются в конце 08.09).

## 1. Гранулярность: дубли строк по order_id

- **Проблема:** одна строка `user_actions` — это действие, а не заказ.
  По одному `order_id` может быть несколько строк (create + cancel).
- **Проверка:** сравнили `COUNT(*)` по action с `COUNT(DISTINCT order_id)`.
- **Результат:**
  - `create_rows` = 59 595, `create_orders` (distinct) = 59 595 → дублей нет;
  - `cancel_rows` = 2 979, `cancel_orders` (distinct) = 2 979 → дублей нет.
- **Решение:** несмотря на отсутствие дублей сейчас, все метрики
  считаются через агрегацию по `order_id` (`COUNT(DISTINCT order_id)` /
  CTE `creates` + `cancels`). Причины: (1) защита от дублей при
  изменении источника; (2) гранулярность «заказ», а не «строка» —
  продуктово корректное определение метрики.
- **Влияние:** без схлопывания cancel rate мог бы завышаться при
  появлении дублей.

## 2. Аномалии «отмена раньше создания»

- **Проблема:** в CSV встречаются строки, где `cancel_order` стоит
  раньше `create_order` (order 13, 390, 395 и др.).
- **Проверка:** сравнили `MIN(time)` по `cancel_order` и `create_order`
  для каждого `order_id`; посчитали заказы, где `canceled_at < created_at`.
- **Результат:** **0 аномалий**. Во всех 2 979 отменённых заказах
  отмена происходит после создания.
- **Вывод:** случаи «cancel раньше create» в файле — это **порядок
  строк в CSV**, а не временная аномалия. При агрегации через `MIN(time)`
  всё встаёт на места.
- **Решение:** заказ считается отменённым при наличии любого
  `cancel_order` по `order_id`; дополнительных фильтров не требуется.

## 3. Пропуски в birth_date

- **Проблема:** часть пользователей без даты рождения.
- **Проверка:** `COUNT(*) FILTER (WHERE birth_date IS NULL)`.
- **Результат:** 50 из 20 331 пользователей (**0,25 %**).
- **Решение:** при сегментации по возрасту такие пользователи
  попадают в группу `unknown`; в общем cancel rate учитываются.
- **Влияние:** пропуски < 1 % — возрастная сегментация остаётся
  надёжной, существенного искажения не вносит.

## 4. Формат birth_date: ДД/ММ/ГГ и «век»

- **Проблема:** год в `birth_date` двузначный (`24/05/91`).
  Непонятно, 1991 или 2091.
- **Решение:** правило парсинга — если `YY > 22`, то `1900 + YY`,
  иначе `2000 + YY` (на 2022 год: 23 → 1923, 22 → 2022).
- **Влияние:** без правила пользователи 2000-х получили бы возраст
  100+ и попали в группу «45+», исказив сегментацию.

## 5. Возрасты вне разумного диапазона

- **Статус:** проверяется на этапе сегментации (нужен парсинг
  `birth_date`). Будут зафиксированы пользователи с возрастом
  < 18 и > 90; при необходимости — оговорка в «Ограничениях».
  
## 6. Заказы от пользователей вне справочника users («сироты»)

- **Проблема:** в `user_actions` есть `user_id`, которых нет в `users`.
- **Проверка:** LEFT JOIN user_actions → users, WHERE users.user_id IS NULL.
- **Результат:** **3 228 заказов** (5,4 % от 59 595) от пользователей
  без записи в справочнике. Демографии (пол, возраст) по ним нет.
- **Решение:** в сегментации по полу и возрасту вынесены в отдельную
  группу `unknown`; в общем cancel rate учитываются (они часть
  числителя и знаменателя).
- **Влияние:** 5,4 % заказов не участвуют в демографической
  сегментации — оговорено в «Ограничениях». Причины «сиротства»
  требуют проверки на продукте (регистрация без профиля,
  удалённые аккаунты, ошибка экспорта).
